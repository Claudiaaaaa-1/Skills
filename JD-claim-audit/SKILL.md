# 商品主张—证据一致性核验

## 这个 skill 回答什么

回答的是一个刻意收窄的问题：

> 这一页里哪些表达构成**可验证的主张**，每条主张最可信的证据是什么，证据与主张之间是否存在**可解释的信息断裂**，以及当前信息够不够支撑一个动作。

刻意不回答「这个商品是不是假的」。真伪判断需要实物、检测、客诉等系统外的真值，模型在没有这些信号时只能猜，而猜测会同时制造漏放和商家投诉。把问题收窄成「关系是否成立」，结论才可复核、可申诉、可回归测试。

输入是一个 SPU/SKU 的页面快照（文本 + 结构化属性 + 资质材料），输出是主张台账、证据台账、断裂说明、四态决策和一份能力边界声明。**台账不是可选的漂亮附件，它是这个 skill 的主要产物**——《广告法》第 8、11、38 条要求内容准确、引证表明出处、证明文件齐全，见 `references/compliance.md`。

## 工作流

**第 1 步 · 页面解析。** 把页面切成标题、主图 OCR、结构化属性、详细描述、规则、资质材料六类信息块，保留每块的原始出处。用 `scripts/parse_page.py`，它做确定性切块，不做判断。信息块来源决定后续证据的可信度级别，所以不要在这里做有损归并。

**第 2 步 · 主张抽取。** 由模型完成。把每条表达拆成一条或多条主张，区分三类：可验证事实、主观修辞、受约束承诺。一条表达可以拆出多条主张，例如「100%真蚕丝，柔软得像云朵」拆成一条材质占比主张和一条纯表达。把结果写进输入 JSON 的 `claims` 字段，字段定义见 `references/claim-schema.md`。

> 这一步最容易出错的地方是把「100%真蚕丝」当成极限词。它是材质占比主张，真正要验的是材质比例与属性、检测是否一致；当成词，就会重演旧链路的误伤。

**第 3 步 · 证据对齐。** 用 `scripts/align.py`。按主张对象、时间、范围（规格/批次/地区）、数值、资质挂接证据，并记录对齐状态。证据分三级：强事实（结构化属性、可核验编号）、需交叉验证（商家自填参数、资质图片）、纯表达（营销话术）。对齐维度不是形式主义——《广告法》第 11 条要求引证表明出处并明示适用范围与有效期限。

**第 4 步 · 断链判断。** `align.py` 会给出断裂候选，模型负责裁定并补上解释。事实、解释、判断三者分开写：事实是「主张写 100%，属性写聚酯纤维」，解释是「二者不可同时成立」，判断是「不可接受」。分开是因为上游出错时要能分清是抽取错、对齐错还是判断错。

证据缺失时标 `UNKNOWN`，不要替商家补一个结论。这一步的克制直接决定了会不会产生虚假放行。

**第 5 步 · 风险决策。** 用 `scripts/route.py`。四种状态：`PASS`、`BLOCK`、`REQUEST_EVIDENCE`、`HUMAN_REVIEW`。规则用于召回和打标，不用于终判；只有黄赌毒一类硬红线允许短路。原因是词库规则本身就是「100%真蚕丝」被误拦的来源，若规则先出终判，语义纠偏就没有机会发生。

一页多主张时逐条给状态，页面级状态取最严重者，但**不得**用页面级状态覆盖主张级结果。整页粗暴定性会同时制造漏放与误伤。

## 输出契约

输出一个 JSON 台账，顶层必须包含 `page`、`claims`、`evidence`、`gaps`、`decision`、`boundary`。完整字段见 `references/claim-schema.md`。

`boundary` 必填，且要写清当前不能证明什么。没有它，上游很容易把 `PASS` 读成「已核实」，而本 skill 从未核验实物。默认边界声明：

```
未核验检测报告在官方库中的真伪；未覆盖主图与 SKU 的图文关系；未核验实物；单模态文本输入。
```

生成后运行 `scripts/validate_output.py` 校验契约，它会检查必填字段、状态枚举、主张级与页面级状态是否一致、`boundary` 是否存在。

## 离线跑通

不依赖任何 API key。示例输入里 `claims` 已由模型预先抽取（对应第 2 步），脚本负责第 1、3、4、5 步，因此可以直接运行并看到完整台账：

```bash
python3 scripts/audit.py assets/examples/case-01-silk.json --out out.json
python3 scripts/validate_output.py out.json
```

四个示例分别覆盖 `BLOCK`、`PASS`、`REQUEST_EVIDENCE`、`HUMAN_REVIEW`，放在 `assets/examples/`（随安装包分发）。开发源码里 `evals/files/` 是同一批用例的权威副本；官方打包器按规范会排除 `evals/`，所以两处都保留。

接真实页面时，先让模型按 `references/claim-schema.md` 把 `claims` 抽取到 JSON，再交给 `audit.py`。这样不确定性与确定性各待在自己的边界里：模型只做语义抽取和断裂裁定，解析、对齐、路由全部可复现。

## 一个完整例子

输入主张「100%真蚕丝」+ 一条纯表达「柔软得像云朵」，证据是结构化属性「填充物 = 聚酯纤维」。

| 主张 | 对齐结果 | 状态 |
| --- | --- | --- |
| 100%真蚕丝 | 属性表数值 0% 与主张 100% 冲突 | `BLOCK`，理由为数值冲突 |
| 柔软得像云朵 | 纯表达，无证据要求 | `PASS`，标注未核验 |

页面级状态为 `BLOCK`，但第二条主张仍保留 `PASS`。旧链路会去拦「100%」这个极限词，理由完全错了；这里拦的是关系，不是词。

## 能力边界与已知缺口

- 不核验实物资检结果，也不查询官方认证库。资质编号只做格式与有效期校验，「编号格式正确但已注销」这一类漏放**未被消除**，只能标为待核验并转人审。
- 不处理图片内容与图文关系。主图能效标识与属性不一致、升级款图配基础款 SKU 属于已知盲区，必须在 `boundary` 里声明，不能让它被平均准确率掩盖。
- 「补充证据」之后的复审、次数上限、超时、防刷与幂等重跑属于上游链路职责，本 skill 只负责发出状态。

这些缺口不是实现瑕疵，而是当前信息条件下无法诚实地跨过去的边界。把它们写进输出，比让模型猜一个结论更有价值。
